1. Introduction
Dans le cadre de la SAÉ "Application Répartie" (S4-02), notre équipe a conçu et développé une application distribuée permettant l'agrégation et la visualisation d'informations hétérogènes sur la métropole de Nancy. L'objectif principal de ce projet est de faire coopérer différents modules logiciels (interface web, serveur proxy, services distants RMI et base de données) afin de contourner les restrictions de sécurité des navigateurs tout en garantissant la robustesse des échanges réseaux.

Ce compte rendu détaille nos choix techniques, l'architecture mise en place, ainsi que les instructions nécessaires pour déployer et exécuter notre solution sur un environnement Linux.

Application Web Cliente : Développée en TypeScript, elle s'exécute dans le navigateur et affiche une carte interactive (Leaflet). Elle communique de manière asynchrone (Fetch API) avec des API publiques et notre Proxy.

Serveur HTTP (Proxy) : Un serveur intermédiaire développé en Java (HttpServer) qui réceptionne les requêtes du client web et effectue les appels RMI correspondants.

Services RMI et Accès aux Données :

Un service dédié à l'interrogation de la base de données Oracle (hébergée sur Charlemagne) via JDBC.

Un service dédié à la récupération de données externes (incidents de circulation Waze) agissant comme un client HTTP serveur à serveur pour s'affranchir des règles CORS.

Certaines API, comme l'API Waze du Grand Nancy, n'intègrent pas l'en-tête Access-Control-Allow-Origin, bloquant ainsi les requêtes directes depuis notre interface web (erreur CORS Cross-Origin).

3.3. Services RMI (Base de données et Incidents)
Gestion de la Base de données : Nous avons conçu une base de données Oracle en 3FN comprenant les tables Restaurant, TableRestaurant et Reservation. L'accès concurrent lors des réservations est géré par des transactions manuelles (setAutoCommit(false)) et un verrouillage pessimiste (FOR UPDATE sur la table TableRestaurant) pour éviter les conflits.

Récupération des Incidents : Le composant ServiceIncidents utilise le client HTTP natif de Java 11+ (java.net.http.HttpClient) configuré pour passer par le proxy de l'IUT (www-cache:3128) afin de récupérer le fichier JSON des incidents.

5. Analyse Éthique et Sécurité (Contournement CORS)
Le sujet nous invite à réfléchir sur la responsabilité de contourner la politique de sécurité du navigateur en utilisant un proxy backend.

Est-ce responsable ?
Oui, sous réserve de bonnes pratiques. Les politiques CORS (Cross-Origin Resource Sharing) sont mises en place par les navigateurs pour protéger l'utilisateur final contre les attaques CSRF (vol de session, actions à son insu), et non pour protéger l'API distante.
Le contournement via notre service Java (modèle d'architecture BFF - Backend For Frontend) est une pratique standard dans l'industrie pour agréger des API tierces non conçues pour le client.
